  - *Rationale*: The current synchronous blocking call to the external payment provider creates a direct coupling between the Payment Service and an unreliable third-party system. This not only exacerbates latency issues under load (as noted in Step 3) but also limits horizontal scalability, as each request ties up a service thread until response or timeout.  
  - *Improvement*: Replace synchronous HTTP calls with an event-driven pattern using a message queue (e.g., Kafka or AWS SQS). When a payment is initiated, the Payment Service publishes a `PaymentRequest` event to a dedicated topic/queue. A separate, independently scalable worker service consumes these events, processes the external payment call asynchronously, and emits a `PaymentCompleted` event upon completion.  
  - *Scalability Benefits*:  
    - Decouples payment processing from request handling, allowing the Payment Service to scale independently.  
    - Enables burst handling via message buffering, preventing cascading failures during peak loads.  
    - Improves resilience: failed payments can be retried without affecting the client-facing API.  
  - *Integration with Prior Findings*: This directly mitigates the performance bottleneck of synchronous external calls (Step 3) and indirectly reduces pressure on the API Gateway by minimizing long-running requests, thus improving overall system throughput and elasticity.
