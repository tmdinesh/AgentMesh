Based on the **Design Phase** and the **Security Audit** findings, two concrete performance bottlenecks are identified:

     - **Network overhead from unencrypted traffic**: Clear-text Redis sessions require additional TLS handshake overhead when secured (even if not currently enforced), but the absence of encryption means the system is vulnerable to data interception, which can force higher-latency security layers to be retrofitted.

Without connection pooling, each service connection to Redis opens a new TCP socket, increasing latency and CPU overhead due to repeated handshake cycles. This directly impacts API Gateway response times, especially when the authentication service is under load.  

2. **Cache Miss Cascade Due to Inconsistent Caching Strategy & Missing Internal TLS**  
   - The Caching Layer (Redis/Memcached) is used for frequently accessed data, but the lack of internal TLS between microservices introduces **indirect performance degradation**.

This increases the risk of packet loss, replay attacks, and forced retransmissions due to network-level monitoring or misconfiguration in the container environment.  
   - Furthermore, the absence of consistent caching policies (e.g., inconsistent TTLs, lack of cache warming) leads to **high cache miss rates** during peak loads, forcing repeated database queries. This creates a cascading effect: high cache miss → high DB load → increased latency → degraded API response times.  
   - Combined with the **missing input validation at the API Gateway**, malformed or excessive requests can trigger cache invalidation storms or unnecessary cache lookups, amplifying the bottleneck.
